# ADR-015 — سه تب، دو منبعِ دادهٔ واقعی، و یک تب که عمداً خالی است

## Context

پنلِ راست وقتی نودی انتخاب است، یک ستونِ بلند از بخش‌ها نشان می‌داد. خواننده سه تب خواست:
**Status / Diary / Logs**. سؤالِ اصلی این نبود که تب بسازیم یا نه؛ این بود که **هر تب داده‌اش از کجا
می‌آید**، چون قانونِ ۱ می‌گوید فایل‌ها بسترِ حقیقت‌اند و هر چه فایل ندارد، نمایشِ آن یک ادعاست.

## Decision

- **Diary** ← `memory/agents/<node-id>.md`، که در state همان `s.memory.agents[id]` است و با
  `MemoryManager.write` نوشته می‌شود. رنگ‌بندیِ رویدادها از **متنِ خودِ فایل** استخراج می‌شود، نه از یک
  فیلدِ جدید: خطی که با `✗`/`failed` شروع می‌شود قرمز، `⚠`/`warn` هشدار، بقیه سبز. دلیلش این است که اگر
  رنگ را در یک فیلدِ تازه ذخیره کنیم، دو منبعِ حقیقت ساخته‌ایم که می‌توانند از هم جدا بیفتند.
- **Logs** ← `logs/<node-id>/<date>.log`، در state همان `s.logs[id]` (سقفِ ۱۲۰ خط، در `appendLog`).
  خروجی ترمینالی، تک‌رنگ، با همان مُهرِ زمانی که فایل دارد.
- **Status** ← `agent.status`، آخرین خروجی، و خطاها — همه از stateِ موجود. **هیچ نوارِ مصرفِ منبعی اضافه
  نمی‌شود**: مرورگر هیچ عددِ CPU ای نمی‌دهد و `performance.memory` فقط در کروم و تقریبی است. عددِ
  ساختگی از عددِ نبودن بدتر است. این «بعداً» نیست؛ یک تصمیم است و inbox item 1 آن را نگه می‌دارد.
- تبِ فعال **در `ui` state است، نه در فایل** — یک لحظهٔ کار است (قانون ۳ / ADR-009).

## Why

تب یک تغییرِ ظاهری نیست: به خواننده قول می‌دهد که سه جور اطلاعاتِ **مستقل** وجود دارد. اگر یکی‌شان منبع
نداشته باشد، تب فقط یک جای خالیِ شیک است. پس مرزِ تب‌ها را منبعِ داده تعیین می‌کند، نه سلیقه.

## Consequences

- نودی که هرگز اجرا نشده، Diary و Logsِ **خالی** دارد و تب یک پیامِ صادق نشان می‌دهد («nothing written
  yet»)، نه یک placeholder که وانمود کند داده هست.
- رنگ‌بندی از متن استخراج می‌شود، پس اگر نویسندهٔ حافظه قالبِ `✗` را عوض کند، رنگ هم عوض می‌شود. این
  پذیرفته است: یک منبعِ حقیقت بهتر از دو تاست.
- هیچ نودِ انتخاب‌نشده → «Select a node to inspect».
