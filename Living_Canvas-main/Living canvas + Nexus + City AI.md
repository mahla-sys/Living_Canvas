# سند معماری Living Canvas

> این سند به عنوان مرجع کامل برای ساخت سیستم «Living Canvas» نوشته شده است.  
> هدف: هر هوش مصنوعی یا توسعه‌دهنده‌ای که این سند را می‌خواند، بتواند بدون نیاز به توضیح اضافه، معماری، ساختار داده، رفتار سیستم و مسیر توسعه را درک کند.

---

## ۱. تعریف و چشم‌انداز

**Living Canvas** یک بوم بی‌نهایت زنده است که در آن:

- گراف، زبان مادری تفکر است.
- هر گره و یال، هم‌زمان هم طراحی است و هم اجرا.
- کاربر می‌تواند نقاشی کند، نود بسازد، با هوش مصنوعی گفتگو کند و سیستم را تغییر دهد.
- هیچ فاصله‌ای بین «نقشه» و «واقعیت اجرایی» وجود ندارد.

این سیستم نه یک ابزار طراحی، نه یک داشبورد، نه یک نرم‌افزار مدیریت پروژه است.  
بلکه **زیرساختی برای فکر کردن، ساختن و دیدن فرایندها به صورت زنده** است.

---

## ۲. اصول بنیادین

### ۲.۱ طراحی = اجرا

- آنچه روی بوم دیده می‌شود، همان چیزی است که اجرا می‌شود.
- تغییر گراف به معنای تغییر مستقیم سیستم است.
- نیاز به ترجمه بین «طراحی» و «کد» حذف می‌شود.

### ۲.۲ منبع حقیقت: فایل‌های Markdown + Frontmatter

- هر نود در بوم، در واقع یک فایل Markdown است.
- هر فایل یک بخش YAML Frontmatter دارد که تمام اطلاعات نمایشی، مکانی و رفتاری نود را نگه می‌دارد.
- فایل‌ها قابل نسخه‌برداری با Git، قابل مشاهده در Obsidian و قابل ویرایش توسط انسان یا هوش مصنوعی هستند.

### ۲.۳ هوش مصنوعی، همکار فعال است

- هوش مصنوعی فقط متن نمی‌دهد؛ از طریق Function Calling مستقیماً روی گراف عمل می‌کند.
- همه ابزارهایی که در اختیار کاربر است، در اختیار هوش مصنوعی نیز هست.
- هوش مصنوعی می‌تواند نود بسازد، ویرایش کند، حذف کند، یال بکشد، نقاشی را به گراف تبدیل کند و وضعیت بوم را بخواند.

### ۲.۴ آزادی نمایش

- هر نود می‌تواند شکل‌ها، رنگ‌ها، ضخامت‌ها، شفافیت و انیمیشن‌های متفاوت داشته باشد.
- هر نود می‌تواند در حالت‌های مختلف دیده شود: نقطه، نام، کارت، گفتگو، Markdown و غیره.
- کاربر عاشق انتخاب است؛ سیستم نباید محدودش کند.

## ۳. مفاهیم اصلی

### ۳.۱ نود (Node)

نود واحد پایه در Living Canvas است.  
هر نود یک موجودیت با هویت، موقعیت، شکل، رنگ، انیمیشن و محتوای Markdown است.

#### انواع اولیه نود

| type | توضیح |
|---|---|
| `note` | یادداشت ساده |
| `concept` | مفهوم یا ایده |
| `persona` | شخصیت / نقش |
| `system` | سیستم یا زیرسیستم |
| `data` | داده یا خروجی |
| `agent` | عامل هوش مصنوعی |
| `folder` | پوشه‌ای از نودهای دیگر |
| `unknown` | ناشناخته‌ها و جای خالی برای چیزهایی که هنوز نام ندارند |

### ۳.۲ یال (Edge)

یال نشان‌دهنده ارتباط یا جریان بین دو نود است.

#### انواع اولیه یال

| type | توضیح |
|---|---|
| `flow` | جریان داده یا اجرا |
| `relation` | ارتباط مفهومی |
| `feeling` | ارتباط احساسی/شخصی |
| `logical` | ارتباط منطقی |
| `event-flow` | جریان رویداد بین ایجنت‌ها (برای Nexus) |

### ۳.۳ نقاشی آزاد (Stroke)

- کاربر می‌تواند آزادانه روی بوم نقاشی بکشد.
- نقاشی‌ها گراف نیستند؛ فقط عناصر بصری هستند.
- هر نقاشی به صورت یک فایل JSON جدا ذخیره می‌شود.
- فقط وقتی کاربر از هوش مصنوعی بخواهد، نقاشی به گراف تبدیل می‌شود.

## ۴. ساختار فایل‌ها و پوشه‌ها

هر پروژه یک پوشه است.  
درون پوشه، فایل‌های Markdown و پیکربندی‌های مرتبط قرار دارند.

```
/projects/
└── my-project/
    ├── canvas.yaml          ← تنظیمات اصلی بوم
    ├── nodes/
    │   ├── node-001.md
    │   ├── node-002.md
    │   └── ...
    ├── edges.yaml           ← یال‌ها (یا در Frontmatter نودها)
    ├── strokes/
    │   ├── stroke-001.json
    │   └── stroke-002.json
    └── assets/
        └── ...
```

## ۵. ساختار Frontmatter یک نود

هر نود یک فایل Markdown است که بخش YAML در ابتدای آن تمام اطلاعات لازم را دارد.

```markdown
---
id: "node-001"
title: "mahla"
type: "persona"
path: "/projects/my-project/nodes"
position:
  x: 200
  y: 300
  z: 0
shape: "circle"
color: "#8b5cf6"
animation:
  type: "breathe"
  speed: 1.0
  color: "#a78bfa"
viewMode: "card"
connections:
  - target: "node-002"
    type: "relation"
    label: "تغذیه می‌کند"
style:
  strokeColor: "#000000"
  strokeWidth: 2
  fillStyle: "solid"
  opacity: 100
---
# mahla

محتوای Markdown آزاد...
```

### فیلدهای Frontmatter

| فیلد | توضیح |
|---|---|
| `id` | شناسه یکتا |
| `title` | عنوان نمایشی |
| `type` | نوع نود از جدول انواع |
| `path` | مسیر پوشه‌ای فایل در سیستم |
| `position` | مختصات روی بوم (x, y, z) |
| `shape` | شکل نود: rectangle, circle, diamond, hexagon, card, empty |
| `color` | رنگ اصلی |
| `animation` | تنظیمات انیمیشن |
| `viewMode` | حالت نمایش: dot, name, card, chat, markdown |
| `connections` | آرایه‌ای از یال‌ها به دیگر نودها |
| `style` | استایل‌های بصری مانند ضخامت خط، شفافیت و ... |

## ۷. معماری نرم‌افزاری

### ۷.۱ لایه‌ها

| لایه | مسئولیت | پیشنهاد |
|---|---|---|
| **UI** | نمایش بوم، نودها، پنل‌ها | React + React Flow + Tailwind |
| **State Management** | مدیریت وضعیت گراف و تعاملات | Zustand |
| **File Adapter** | تبدیل نودها به فایل‌های Markdown و بالعکس | TypeScript |
| **Persistence** | ذخیره‌سازی محلی در مرورگر | IndexedDB (فاز اول) / سیستم فایل (بعداً) |
| **AI Tools** | رابط هوش مصنوعی برای دستکاری گراف | Function Calling |
| **Event Bus** | مدیریت رویدادهای بین نودها و ایجنت‌ها | mitt یا Pub/Sub دست‌ساز |

### ۷.۲ جریان داده

1. کاربر یک نود می‌سازد یا ویرایش می‌کند.
2. Zustand وضعیت گراف را به‌روزرسانی می‌کند.
3. Adapter وضعیت جدید را به صورت فایل Markdown ذخیره می‌کند.
4. اگر هوش مصنوعی بخواهد تغییری دهد، ابزار مناسب را صدا می‌زند.
5. Event Bus رویدادهای لازم را منتشر می‌کند و ایجنت‌ها را بیدار می‌کند.

## ۸. ابزارهای هوش مصنوعی

هوش مصنوعی با استفاده از Function Calling این ابزارها را در اختیار دارد:

### ۸.۱ `create_node`

- پارامترها: `label`, `type`, `x`, `y`, `shape`, `color`, `animation`, `viewMode`
- خروجی: ساخت فایل Markdown جدید و افزودن نود به بوم

### ۸.۲ `update_node`

- پارامترها: `id`, هر کدام از فیلدهای Frontmatter
- خروجی: به‌روزرسانی فایل Markdown و نود روی بوم

### ۸.۳ `delete_node`

- پارامترها: `id`
- خروجی: حذف فایل مربوطه و حذف نود و یال‌های متصل از بوم

### ۸.۴ `create_edge`

- پارامترها: `source`, `target`, `type`, `label`
- خروجی: افزودن یال به `edges.yaml` یا Frontmatter

### ۸.۵ `delete_edge`

- پارامترها: `id`
- خروجی: حذف یال

### ۸.۶ `get_graph_snapshot`

- خروجی: وضعیت کامل نودها و یال‌ها برای تحلیل

### ۸.۷ `convert_strokes_to_graph`

- پارامترها: `strokeIds`
- خروجی: تبدیل نقاشی‌های انتخاب‌شده به نود و یال

- نمایش وضعیت ایجنت‌ها

### فاز ۴ — پنل‌های جانبی و viewMode

- پنل چت برای ایجنت‌ها

- لایه نقاشی

- تنظیمات انیمیشن در Frontmatter

## ۱۲. نکات مهم برای توسعه‌دهنده

- هر نود باید یک شناسه یکتا داشته باشد.
- تغییرات گراف باید قابل Undo/Redo باشند.
- همه اطلاعات نمایشی در Frontmatter ذخیره می‌شود.
- هوش مصنوعی فقط با ابزارهای تعریف‌شده عمل می‌کند.
- نقاشی‌ها تا وقتی تبدیل نشده‌اند، گراف نیستند.
- سیستم باید فضایی برای ناشناخته‌ها داشته باشد.

- هر نود یک فایل Markdown است.
- هوش مصنوعی می‌تواند همان‌طور که کاربر می‌سازد، بسازد.

# سند معماری Nexus و شهر زنده

> این سند ادامه‌ی سند معماری Living Canvas است و به عنوان مرجع کامل برای ساخت سیستم عامل ایجنتی «Nexus» و مفهوم «شهر زنده» در دل Living Canvas نوشته شده است.  
> هدف: هر هوش مصنوعی یا توسعه‌دهنده‌ای که این سند را می‌خواند، بتواند بدون ابهام، معماری، ساختار داده، رفتار ایجنت‌ها، رویدادها و یکپارچگی آن با Living Canvas را درک کند.

---

## ۱. تعریف و چشم‌انداز Nexus

**Nexus** یک سیستم عامل ایجنتی (Agent Operating System) است که در مرکز Living Canvas قرار می‌گیرد.  
این سیستم از چندین **شرکت** (تیم‌های ایجنتی) تشکیل شده که هر کدام وظیفه‌ی مشخصی در فرایند حل مسئله و ساخت پروژه دارند.

هر شرکت یک مجموعه از عامل‌های هوش مصنوعی است که بر اساس یک خط لوله‌ی مرحله‌ای کار می‌کنند.  
Nexus به کاربر کمک می‌کند تا از یک ایده‌ی خام به یک نقشه‌ی اجرایی کامل برسد و در نهایت پروژه را بسازد.

**شهر زنده** استعاره‌ای برای نمایش این ایجنت‌ها به صورت موجودیت‌های زنده در Living Canvas است: هر ایجنت یک شهروند با مغز، ابزار، شغل و رفتار قابل مشاهده است که می‌توان با آن تعامل کرد، به آن ابزار داد، یا گونه‌های جدیدی از آن ایجاد کرد.

---

## ۲. شرکت‌های Nexus

در نسخه‌ی فعلی، Nexus از ۷ شرکت تشکیل شده است که هر کدام یک گام از فرایند را انجام می‌دهند:

| شرکت | نام | وظیفه | خروجی |
|---|---|---|---|
| ۱ | فهم مسئله | گفتگو با کاربر برای شفاف‌سازی دقیق هدف و مسئله | خلاصه و جامع از مسئله |
| ۲ | جستجو و ایده‌پردازی | تحقیق، تولید ایده، و نظم‌دهی به داده‌ها | مجموعه‌ی راه‌حل‌های ممکن |
| ۳ | انتخاب مسیر | تحلیل گزینه‌ها و انتخاب سه راه اصلی، سپس انتخاب نهایی با کاربر | مسیر انتخاب‌شده |
| ۴ | استخراج جزئیات | بر اساس مسیر، تمام فانکشن‌ها، فریم‌ورک‌ها، و جزئیات فنی را لیست می‌کند | سند جزئیات فنی |
| ۵ | ساخت رودمپ درختی | تبدیل جزئیات به یک ساختار درختی از بالا به پایین | درخت رودمپ (شامل معماری، زیرساخت، فانکشن‌ها) |
| ۶ | طراحی معماری | تعیین معماری سیستم، تصمیمات زیرساختی، و چیدمان ماژول‌ها | سند معماری نهایی |
| ۷ | ساخت و اجرا | بر اساس نقشه، پروژه را می‌سازد (با تیم ایجنتی) | کد و خروجی نهایی |

**نکته:** این ۷ شرکت لزوماً خطی نیستند؛ ممکن است بازگشت به عقب یا اجرای موازی در آینده اضافه شود. اما در نسخه‌ی اولیه، ترتیب مشخصی دارند.

## ۳. معماری Blackboard و ارتباط رویدادمحور

### ۳.۱ اصول

- هیچ ایجنتی مستقیماً با ایجنت دیگر صحبت نمی‌کند.
- تمام ارتباطات از طریق یک **Blackboard** (تخته‌سیاه) که همان سیستم فایل است انجام می‌شود.
- هر ایجنت خروجی خود را روی Blackboard می‌نویسد و یک **رویداد** منتشر می‌کند.
- ایجنت بعدی که مشترک آن رویداد است، بیدار شده و از Blackboard می‌خواند.

### ۳.۲ Blackboard = پوشه‌ی پروژه

```
/nexus/projects/my-project/
├── core/
│   ├── problem/
│   │   ├── summary.md        ← خلاصه از شرکت ۱
│   │   └── full.md           ← جامع از شرکت ۱
│   ├── ideas/
│   │   ├── idea-001.md
│   │   ├── idea-002.md
│   │   └── ...
│   ├── decision/
│   │   └── chosen-path.md
│   ├── details/
│   │   └── technical-details.md
│   ├── roadmap/
│   │   └── tree.md           ← ساختار درختی
│   ├── architecture/
│   │   └── architecture.md
│   └── implementation/
│       ├── code/
│       └── logs/
└── agents/
    ├── company-1/
    │   ├── config.yaml
    │   ├── prompt.md
    │   └── tools.json
    ├── company-2/
    └── ...
```

### ۳.۳ رویدادها

هر رویداد یک پیام ساده با نام و payload است که روی Event Bus منتشر می‌شود.

نمونه رویدادها:

- `company1.done`  
- `company2.done`  
- `decision.made`  
- `roadmap.generated`  
- `agent.status.changed`

ایجنت‌ها با اشتراک در رویدادهای مشخص، بیدار می‌شوند.  
این بیدار شدن در Living Canvas با انیمیشن نور بین نودها نمایش داده می‌شود.

## ۴. داده‌ها و Frontmatter در Nexus

### ۴.۱ نود شرکت (Company Node)

هر شرکت یک نود از نوع `agent` با `agentType: "company"` است.

```markdown
---
id: "company-1"
title: "شرکت ۱"
type: "agent"
agentType: "company"
position: { x: 100, y: 200 }
shape: "rectangle"
```

### ۴.۲ نود خروجی (Output Node)

خروجی‌های هر شرکت به صورت نودهای `note` یا `data` با `source: "company-1"` ذخیره می‌شوند.

```markdown
---
id: "output-001"
title: "خلاصه مسئله"
type: "data"
source: "company-1"
position: { x: 150, y: 350 }

  path: "/nexus/projects/my-project/core/problem/summary.md"
  summary: "کاربر می‌خواهد یک اپلیکیشن برای مدیریت پروژه بسازد..."
---
# خلاصه مسئله

محتوای کامل...
```

### ۴.۳ نود ایجنت منفرد (Individual Agent)

در داخل هر شرکت، ممکن است چند ایجنت با وظایف ریزتر وجود داشته باشند.  
آن‌ها نیز به عنوان نودهای `agent` با `agentType: "individual"` نمایش داده می‌شوند.

```yaml
agent:
  systemPrompt: "..."
  tools: ["search", "code"]
  memory: "..."
  status: "working"
  subscribedEvents: ["company1.done"]
  publishEvents: ["company2.done"]
```

## ۵. مفهوم شهر زنده

### ۵.۱ ایجنت‌ها به عنوان شهروندان

هر ایجنت یک موجودیت زنده است با:

- **مغز** : پرامپت، حافظه، ابزارها
- **قلب** : وضعیت فعلی (idle, working, done)
- **بدن** : شکل، رنگ، انیمیشن، موقعیت
- **رد پا** : تاریخچه‌ی کارها و رویدادها

### ۵.۲ تعامل کاربر

- کاربر می‌تواند روی هر ایجنت کلیک کند و پنل چت آن را باز کند، ببیند چه فکر می‌کند، خروجی‌ها را مرور کند، و حتی مستقیماً با آن صحبت کند.
- کاربر می‌تواند به هر ایجنت ابزار جدید بدهد (مثل اتصال به API)، پرامپت آن را تغییر دهد، یا آن را به ایجنت دیگری متصل کند.
- کاربر می‌تواند «گونه‌های جدید» از ایجنت بسازد: یک نود جدید از نوع `agent` بکشد، پرامپت و ابزارها را تنظیم کند و به شبکه متصل کند.

### ۵.۳ اتصال و جریان

- بین ایجنت‌ها یال‌هایی از نوع `event-flow` وجود دارد که نشان‌دهنده‌ی بیدار شدن یکی توسط دیگری است.
- وقتی ایجنت A کارش تمام می‌شود، یک رویداد منتشر می‌کند؛ نود B با انیمیشن `flow` روشن می‌شود.
- کاربر می‌تواند فیلترها و شرط‌هایی روی یال‌ها بگذارد (مثلاً فقط اگر خروجی شامل X بود، به ایجنت بعدی برو).

## ۶. یکپارچگی با Living Canvas

### ۶.۱ نود Nexus

- در Living Canvas، یک نود ویژه به نام `Nexus` وجود دارد که نمایانگر کل سیستم ایجنتی است.
- با دابل‌کلیک روی آن، بزرگ‌تر شده و ۷ شرکت داخلش دیده می‌شوند.
- هر شرکت خروجی‌هایش را به صورت نودهای زیر خودش می‌سازد.

### ۶.۲ نودهای شرکت

- هر شرکت یک نود مستطیلی با رنگ مخصوص است.
- درون نود، نام شرکت و وضعیت فعلی (مثلاً "در حال کار") نمایش داده می‌شود.
- با کلیک روی شرکت، پنل چت همان شرکت باز می‌شود و تاریخچه‌ی گفتگوها و ابزارها نمایش داده می‌شود.

### ۶.۳ نودهای خروجی

- خروجی‌های هر شرکت (خلاصه، تصمیم، جزئیات، درخت و...) به صورت نودهای کوچک با شکل‌های متفاوت زیر شرکت قرار می‌گیرند.
- هر خروجی یک فایل Markdown است که در Blackboard ذخیره می‌شود و در Living Canvas به صورت زنده دیده می‌شود.
- کاربر می‌تواند خروجی را ویرایش کند و تغییرات به سیستم فایل اعمال می‌شود.

### ۶.۴ نقاشی و ارتباطات دستی

- کاربر می‌تواند علاوه بر نودهای خودکار نکسوس، نودهای دستی، نقاشی و یادداشت‌های خود را در همان بوم اضافه کند.
- هوش مصنوعی می‌تواند بین نودهای دستی و نودهای نکسوس ارتباط برقرار کند (مثلاً یک ایده‌ی کاربر را به یک خروجی شرکت متصل کند).

## ۷. معماری فنی Nexus

### ۷.۱ Event Bus

- از یک Pub/Sub سبک (مانند mitt) در فرانت‌اند استفاده می‌شود.
- در نسخه‌ی آینده که Backend جدا داشته باشیم، می‌توان از Redis Pub/Sub یا MQTT استفاده کرد.

### ۷.۲ ابزارهای هوش مصنوعی برای ایجنت‌ها

هر ایجنت علاوه بر ابزارهای پایه‌ی Living Canvas (ساخت نود، ویرایش و ...)، ابزارهای تخصصی خود را دارد:

- `read_file`: خواندن فایل از Blackboard
- `write_file`: نوشتن فایل در Blackboard
- `search_web`: جستجو در اینترنت (اختیاری)
- `call_api`: فراخوانی API خارجی
- `run_code`: اجرای کد

### ۷.۳ وضعیت ایجنت‌ها

| وضعیت | نمایش | انیمیشن |
|---|---|---|
| `idle` | خاکستری، بی‌نور | `none` |
| `working` | آبی با ضربان | `pulse` |
| `done` | سبز با تنفس | `breathe` |
| `error` | قرمز با لرزش | `shimmer` |

### ۷.۴ ذخیره‌سازی و همگام‌سازی

- تمام داده‌های Nexus روی سیستم فایل (یا IndexedDB در فاز اول) ذخیره می‌شود.
- Living Canvas با File Adapter این داده‌ها را می‌خواند و به نودهای گراف تبدیل می‌کند.
- هر تغییر ایجنت یک رویداد است که در Event Log ثبت می‌شود و می‌توان آن را Undo/Redo کرد.

## ۸. فازهای توسعه Nexus + شهر زنده

### فاز ۰ — زیرساخت اولیه

- راه‌اندازی Event Bus

- گونه‌های متنوع ایجنت
- آواتارهای بصری، انیمیشن‌های پیشرفته
- امکان مشاهده‌ی تاریخچه‌ی کامل هر ایجنت
- شبیه‌سازی و پیش‌بینی رفتار ایجنت‌ها

## ۹. نمونه‌ی سناریو: ساخت یک اپلیکیشن

1. کاربر در Living Canvas یک نود `Nexus` می‌سازد و عنوان پروژه را می‌دهد: "اپ مدیریت کارهای شخصی".
2. نود Nexus باز می‌شود و ۷ شرکت دیده می‌شوند.
3. شرکت ۱ (فهم مسئله) بیدار می‌شود و با کاربر گفتگو می‌کند.  
   پس از پایان، دو فایل `summary.md` و `full.md` در پوشه‌ی `core/problem` ذخیره می‌شود و یک رویداد `company1.done` منتشر می‌شود.
4. نود شرکت ۲ با انیمیشن نور روشن می‌شود.  
   ایجنت‌های داخل شرکت ۲ جستجو می‌کنند، ایده می‌دهند و خروجی‌ها را در `core/ideas` می‌نویسند.
5. شرکت ۳ سه گزینه‌ی اصلی را انتخاب می‌کند و پس از تایید کاربر، مسیر نهایی را در `core/decision` ذخیره می‌کند.
6. شرکت ۴ جزئیات فنی را استخراج می‌کند: فریم‌ورک‌ها، کتابخانه‌ها، فانکشن‌ها.
7. شرکت ۵ یک درخت رودمپ می‌سازد: از کلیات تا فانکشن‌ها.
8. شرکت ۶ معماری را طراحی می‌کند و ساختار ماژول‌ها را مشخص می‌کند.
9. شرکت ۷ شروع به کدنویسی می‌کند و فایل‌های پروژه را در `core/implementation/code` می‌سازد.

در تمام این مراحل، کاربر می‌تواند روی هر شرکت کلیک کند، روند کار را ببیند، در هر مرحله نظر بدهد و تغییرات لازم را اعمال کند.

## ۱۰. جمع‌بندی

Nexus یک سیستم ایجنتی مرحله‌ای است که در Living Canvas به صورت یک شهر زنده از ایجنت‌ها نمایش داده می‌شود.  
معماری Blackboard + Event-Driven باعث decoupling کامل ایجنت‌ها می‌شود و قابلیت توسعه و شخصی‌سازی بی‌نهایت را فراهم می‌کند.

Living Canvas و Nexus با هم یک اکوسیستم فکری-اجرایی می‌سازند که در آن:

- **فکر کردن** = کشیدن نود و نقاشی
- **تصمیم گرفتن** = گفتگو با ایجنت‌ها
- **ساختن** = اجرای خط لوله‌ی ایجنتی
- **دیدن** = مشاهده‌ی همه‌چیز به صورت زنده و نورانی

این سند، مرجع کامل برای ساخت این اکوسیستم است و می‌تواند به عنوان نقشه‌ی راه برای تیم توسعه و هوش مصنوعی مورد استفاده قرار گیرد.
